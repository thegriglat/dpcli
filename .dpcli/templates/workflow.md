# Как ведётся работа над {{project}} (процесс с агентами)

Внутренний документ. Короткая выжимка — в `CLAUDE.md` в корне. Журнал, задания, ветки и документы — через `{{cli}}` (справка — `{{cli}} -h` и `.dpcli/README.md`).

## Роли
- **Пользователь (автор)** — заказчик и автор решений: идеи, выбор между вариантами, границы решения, приёмка. Обсуждает и контролирует через главную сессию. Решает развилки, которые план не закрывает.
- **Главная сессия (глобальный координатор)**:
  - превращает запросы пользователя в планы (сама или через исследователя/планировщика), задаёт вопросы по плану одним списком;
  - на модуль/направление заводит ветку и копию (`{{cli}} module new <модуль>`) и запускает **одного координатора модуля** (`dp-coordinator`); мелкие одиночные задачи — сразу исполнителю в своей копии;
  - решения пользователя пишет через `{{cli}} decide <модуль> "…" --by user --why "…" --plan` (и в журнал, и в план), ответы на шлюзы — `{{cli}} questions` / `{{cli}} answer <Qn> "…"`; координатору в сообщении — коротко «см. `{{cli}} inbox`» (без пересказа от себя как решения); правки плана и контрактов — `{{cli}} plan edit … --commit`;
  - ветки и копии — `{{cli}} sync <модуль>` (влить `{{main_branch}}`), `{{cli}} merge <ветка> [--push]` (после одобрения пользователя; слияние в `{{main_branch}}` сам обновляет смысловой индекс в фоне, `--no-index` — нет), `{{cli}} gc [--remove]` (влитые копии);
  - каждые 30 минут — отчёт о статусе: `{{cli}} status --since 30m` (агент `dp-status` — только если нужен разбор зависаний), итог дня — `{{cli}} digest --since today`;
  - вливает ветки в `{{main_branch}}` после одобрения пользователя, пушит и выпускает версии — по его команде.
- **Координатор модуля** (`dp-coordinator`) — держит план модуля и журнал хода работ (`{{plan_dir}}/<модуль>/` через `{{cli}}`, раздел «Журнал и задания»), **до запуска исполнителей формулирует контракты** (ниже), раздаёт задачи исполнителям — одна задача = один свежий исполнитель в своей рабочей копии, — принимает по условиям приёмки (`{{cli}} accept` + при необходимости вердикт ревьюера, раздел «Приёмка»), приходит к главной сессии на шлюзах. Сам код не пишет и **не ревьюит** (код и диффы задач не читает).
- **Исполнитель** (агенты с `dpcli_role: executor`; из коробки `dp-engineer`, `dp-researcher`, `dp-writer`, `dp-mechanic`) — одна задача в рамках контракта, в своей рабочей копии; отчёт по условиям приёмки.
- **Ревьюер** (`dp-reviewer`) — свежий агент с пустым контекстом на одну задачу исполнителя с `dpcli_review: true` после PASS в `{{cli}} accept`: читает карточку, план, контракты, отчёт и дифф ветки, выборочно перезапускает проверки; вердикт `accept|rework` с замечаниями — в журнал (`{{cli}} review`). Ничего не правит и не коммитит.

## Жизненный цикл
1. Идея (пользователь) → при необходимости исследование или прототип (`dp-researcher`, данные сохраняются).
2. План в `{{plan_dir}}/<модуль>.md`: цель, решения пользователя, предметная модель и её границы, задачи со скоупом, файлами, **условиями приёмки** и оценкой, волны, риски. Вопросы пользователю — одним списком.
3. Ответы пользователя вписываются в план («Решения пользователя (не обсуждаются)»).
4. Ветка `{{module_branch}}` + рабочая копия модуля от `{{main_branch}}` (`{{cli}} module new <модуль>`); координатор модуля.
5. **Контракты** — до первого исполнителя (ниже).
6. Волны задач (≤ ~4 исполнителя одновременно); у каждой задачи карточка (`{{cli}} task new`), своя копия и ветка `<модуль>/<задача>` от `{{module_branch}}`; приёмка — `{{cli}} accept` → по риску `dp-reviewer` (раздел «Приёмка») → решение координатора, merge в `{{module_branch}}`, прогон затронутых проверок (`{{cli}} accept --here`), удаление копии.
7. **Шлюзы**: условие остановки из плана или развилка, которую план не решает, — координатор возвращается с вариантами и рекомендацией; главная сессия спрашивает пользователя; вопрос — `{{cli}} decide <модуль> "…" --ask`, ответ — сообщением координатору и `{{cli}} decide … --by user --answers Qn` (существенное — и в план).
8. Проверка результата пользователем (сборка, вопросы простым языком) → записать ответ, не шлифовать.
9. Слияние `{{module_branch}}` в `{{main_branch}}` после одобрения пользователя; push — по его команде.

## Контракты систем (обязательно для координатора)
Файл `{{contracts_dir}}/<модуль>.md` (или раздел плана) — по каждому стыку между задачами/системами:
- владелец (задача) и потребители;
- точный интерфейс: сигнатуры, формат данных (поля, единицы, системы координат, порядок осей, тип чисел), поведение при отсутствии данных, инварианты;
- версия контракта.
Правила: фиксировать то, что уже есть в коде, а не придумывать заново; расхождения между задачами выявить и раздать; исполнитель работает в рамках контракта; **менять интерфейс — только через координатора**: версия +1, что изменилось, уведомление всех потребителей, их правка в том же шаге. **Контрактные тесты** проверяют форму данных на стыке и ломаются, если формат поменяли без правки контракта.

## Приёмка (координатор не ревьюит сам)
Ревью съедает контекст координатора (чтение кода при сверке, `git diff/show`), поэтому:
1. `{{cli}} report <ID> --show` → `{{cli}} accept <ID>` — детерминированные проверки карточки.
2. FAIL → сразу на доработку (новый исполнитель или тот же с итогом `{{cli}} accept`), ревьюер не нужен.
3. PASS у исполнителя с `dpcli_review: false` (из коробки `dp-writer`, `dp-mechanic`) — принято (`{{cli}} accept` пишет `accepted`). У исполнителя с `dpcli_review: true` (`dp-engineer`, `dp-researcher`) — `{{cli}} accept` пишет `checked`, дальше **по риску** (беречь токены):
   - **без ревьюера** (по умолчанию): координатор читает только отчёт (`{{cli}} report <ID> --show`: сводка, проверки, поле `uncertain` — места, где исполнитель не уверен, и что он проверил) и `git diff --stat` (файлы в скоупе карточки). Сомнения исполнителя выглядят разумно и закрыты проверками → `{{cli}} event <ID> accepted --note "по отчёту"`; нет — вопрос исполнителю или ревьюер.
   - **свежий `dp-reviewer`** — только если: сложная предметная логика/численные схемы/параллельные или GPU-расчёты, стык контракта (формат данных между задачами), задача вернулась на доработку второй раз, или сомнения в `uncertain` серьёзные. Ревьюер разбирает места из `uncertain`, стыки контрактов и формулы, остальное — по `--stat` и выборочно 1–2 места; полное чтение диффа — только для самых сложных задач (более сильная модель). Задание ревьюеру — только: «Ревью задачи <ID>», копия и ветка задачи. Историю, свои догадки и пересказ отчёта не передавать — ревьюер соберёт всё из `{{cli}}`.
4. Ревьюер пишет вердикт `{{cli}} review <ID>` (событие `reviewed`, файл `tasks/<ID>.review.json`; в `{{cli}} status` — `rev:rework 2B`).
5. Координатор решает по вердикту: `accept` → `{{cli}} event <ID> accepted --note "по ревью"` и слияние; `rework` → замечания (`{{cli}} review <ID> --show`) — исполнителю на доработку, после неё снова `{{cli}} accept` и свежий ревьюер. Спорное замечание — вопрос ревьюеру или исполнителю (SendMessage), а не чтение кода самим.

**Координатору запрещено** читать код, диффы (`git diff/show`) и логи задачи ради ревью — это работа `dp-reviewer`. Разрешено: `{{cli}} status/log/report --show/review --show`, итог `{{cli}} accept`, `git diff --stat` при слиянии.

## Общие правила (для всех агентов)
- Агенту остаются только задачи, которые детерминированным скриптом не решить, — подумать: спроектировать, решить, разобрать причину, написать текст/код. Всё, что можно сделать скриптом (поиск, сводки, проверки, перенос, слияние, отчёты по числам), — делает `{{cli}}` или скрипт задачи; повторяющуюся ручную операцию — оформить командой (через обратную связь).
- Детерминированное — командами `{{cli}}`: поиск и работа с планами, журналами, документами, ветками — только через него (`{{cli}} search`, `{{cli}} search --sem` (если включён `sem.enabled`), `{{cli}} plan`, `{{cli}} docs …`, `{{cli}} log`, `{{cli}} status`, `{{cli}} task …`, `{{cli}} sync/merge`); свои grep/python-скрипты для этого не писать (исключение — код проекта и исследовательский код задачи). Не хватило команды — обойти один раз и сразу записать обратную связь (`{{cli}} event <модуль> note --note "dpcli: …"` или поле `dp_feedback`).
- **Корректность прежде «нравится»**: правильность в заявленных границах решения; параметры — с обоснованием (из предметной области, измерений, источников), а не подобранные «чтобы выглядело хорошо»; в документах — какие допущения сделаны и чего решение не умеет. Отзывы пользователей — проверка после, не подгонка.
- **Не шлифовать**: мелкие визуальные и стилистические детали — не больше 2 попыток, берём лучшую.
- **Всё можно менять**, пока проект не объявил совместимость: без миграций и поддержки старых настроек, форматов, флагов ради привычки.
- **Тесты и проверки** — неинтерактивно (без окон и ручного ввода); известные нестабильные падения под нагрузкой — не регрессии, но отметить в отчёте. **Общие замки:** счёты на GPU — под `{{cli}} lock gpu <имя> -- <команда>` или `{{cli}} job --lock gpu start <имя> <таймаут_с> <команда>`; тяжёлые CPU-прогоны (пачки тестов, индексация, подготовка данных) — `{{cli}} lock cpu …` (семафор на N слотов, `DPCLI_CPU_SLOTS`); кто держит — `{{cli}} lock status`. Долгие запуски — `{{cli}} job start|wait|status|stop`.
- **Коммиты** — только свои файлы: `git add <пути> && git commit -m "..." -- <пути>` (индекс общий); сообщения по-русски + строка `Claude-Session: …` из системного напоминания; коммитить на логичных шагах; **не пушить**.
- **Картинки и артефакты** (скриншоты, графики) — в каталог артефактов проекта (`artifacts_dir` конфига, в главной копии), каждая задача в свою подпапку; не в `build/` рабочей копии задачи — он пропадает при удалении копии.
- **Пачки запусков** (подбор параметров, замеры, серии тестов, повторы для частоты): не циклы «запустил → посмотрел → поправил», а сразу весь план одним скриптом → один фоновый прогон с записью по строке на запуск (csv/json, продолжение с места после прерывания) → одно ожидание до конца (без сон-циклов с чтением вывода) → итог одним скриптом (таблица) → разбирать только итог. Большой план — сначала оценить время по 1–2 пробным точкам. Токены тратятся на каждый шаг агента, а не на время расчёта.
- **Массовые данные — с контрактом формата**: формат больших массивов и записей, которыми обмениваются задачи, фиксируется в `{{contracts_dir}}/<модуль>.md` с версией + контрактный тест (имена, формы, типы, единицы, метаданные); выбирать компактный формат со схемой, файл пишется один раз (во временный и переименование в конце) и дальше только читается. Сырые промежуточные данные после упаковки удалять. Журналы, логи, небольшие сводки и конфиги — jsonl/json/csv/md.
- **Долгие запуски** (сборки, прогоны > 1–2 мин) — фоном средствами агента (`run_in_background`, о конце придёт уведомление) или `{{cli}} job start <имя> <таймаут_с> <команда…>` → `{{cli}} job wait <имя>`. **Не** ждать и не убивать по `pgrep -f`/`pkill -f` — они находят сам цикл ожидания и свою оболочку; чужие процессы не трогать (подробно — «Наблюдение»).
- **Бережливость токенов**: токены тратит каждый агент и каждый его шаг, а не время расчёта.
  - Слои: небольшой модуль (2–3 задачи) — без координатора, главная сессия даёт задание исполнителю сама; координатор — для больших модулей.
  - Не останавливать и не перезапускать агентов ради новых правил — передать сообщением (SendMessage); перезапуск = повторное чтение всего контекста.
  - Модели: исполнители по умолчанию — средняя модель (Sonnet); сильная (`model: opus`) — только для сложной предметной логики/численных схем/параллельных расчётов (решает координатор при запуске); самая сильная — планирование и ревью самого сложного.
  - **Картинки** (≈1,5 тыс. токенов каждая) — открывать **только если внешний вид и есть предмет задачи или по запросу пользователя**. Проверка — числами и таблицами из скрипта; графики можно сохранять в файлы для пользователя, но агенты их не открывают.
  - План и контракты — разделами (`{{cli}} plan <модуль> <раздел>`), не целиком; большие планы делить по этапам.
  - Исполнитель в отчёте перечисляет сомнения (`uncertain`) — это фокус приёмки вместо чтения всего диффа.
- **Данные исследований** сохранять и коммитить (таблицы, команды воспроизведения, итоговые картинки); крупное — локально, путь в README.
- **Не выдумывать**: числа — из замеров, результаты агентов — из их отчётов.
- Настройки Claude, права, CLAUDE.md и `.claude/` — не менять (кроме случаев, когда это задача).

## Журнал и задания — `{{cli}}`
Справка — `.dpcli/README.md` (`{{cli}} -h`). Копия `.dpcli/dpcli` в рабочей копии сама перезапускается из главной копии, если там версия новее (`DPCLI_NO_REEXEC=1` — отключить). ID задачи — `<КОД>-<n>[буква]` (`^[A-Z]{2,4}-\d+[a-z]?$`, напр. NN-7, NN-7a); КОД — поле `code` в `module.json` (2–4 заглавные латинские, уникален; `{{cli}} module init <модуль> --code` / `{{cli}} module new --code`); `{{cli}} task new <модуль>` без ID берёт следующий номер; контракты (C1, N1…) — не задачи; старые ID не переименовывать. Журнал модуля — `{{plan_dir}}/<модуль>/`: карточки, отчёты, `events.jsonl`, `decisions.jsonl`; события и решения **только дописываются** командами `{{cli}}` — журнал руками и целиком не переписывать (Write/python-вставки), md-вид для людей — `{{cli}} render <модуль>`.
- Карточка задачи — `{{cli}} task new` (скилл `start-to-do`): цель, контракты с версиями, копия/ветка, скоуп, «не трогать», проверки приёмки `{name, cmd|tests, expect}`. Исполнитель читает `{{cli}} task show <ID>` и нужные разделы плана `{{cli}} plan <модуль> <раздел>`, а не весь план.
- События: `{{cli}} event <ID> started|blocked|cancelled|merged|note`; отчёт исполнителя — `{{cli}} report <ID> < отчёт.json` (схема — `{{cli}} report --template`, неверный не примется) — пишет в копию модуля, это единственное исключение из «чужие копии не трогать»; приёмка — `{{cli}} accept <ID>` (таблица PASS/FAIL, логи в `build/dpcli/<ID>/`, итог — событие), а не чтение кода и логов глазами; ревью — `dp-reviewer` → `{{cli}} review <ID>` (раздел «Приёмка»); решения — `{{cli}} decide`.
- Статус — `{{cli}} status [<модуль>]` (несколько строк: задачи, ветки, «тихо» > 40 мин, вопросы пользователю) вместо опросов `git log/status`; `git diff/show` — только по делу.
- Перед новой работой — `{{cli}} search <текст|regex> [--module М]` по прошлым модулям (карточки, отчёты, события, решения); по смыслу — `{{cli}} search --sem "запрос"` (опционально: `sem.enabled: true` в конфиге + Ollama; нужен `{{cli}} index`; выключен — команда скажет об этом, пользоваться обычным search).
- В начале каждого шага координатор читает `{{cli}} inbox <модуль>` (новые решения пользователя, ответы, правки плана, заметки; метка чтения — `{{plan_dir}}/<модуль>/.read_<читатель>`, в .gitignore); пусто — «нового нет».
- Коммит журнала — координатор, своими путями: `git add {{plan_dir}}/<модуль> && git commit -m "…" -- {{plan_dir}}/<модуль>`.
- **Обратная связь по `{{cli}}`** — обязательно в конце работы: исполнитель — поле `dp_feedback` отчёта, координатор — `{{cli}} event <модуль> note --note "dpcli: …"` (чего не хватило, что неудобно; можно «нет»).

## Документация: куда что класть
Каталог документов — `docs_dir` конфига; точка входа — `INDEX.md` в нём (путь — тип — статус — summary). «Что мы знаем про X»: `{{cli}} docs findings X` (реестр выводов `registry/findings.md`), `{{cli}} docs find [--type T] [--module M] текст`, `{{cli}} search` (и `search --sem`, если включён); не grep.
- Руководства (как устроена система), `{{contracts_dir}}/<модуль>.md` — контракты стыков, исследования (вывод, данные, где применено), `{{plan_dir}}/` — только живые и отложенные планы (`status: idea|postponed`), архив — планы и журналы закрытых работ (не удалять, `git mv`; выводы перед архивированием — в `findings.md`).
- Каждый md в каталоге документов начинается с frontmatter: `type` (guide|plan|contract|research|reference|journal|registry), `status` (active|idea|postponed|closed|superseded), `module`, `updated`, `summary` (1 строка), `related`; research — ещё `conclusion`, `data`, `applied_in`; contract — `contracts: [{id, version}]`. Новому файлу — `{{cli}} docs init`.
- Перед коммитом документов — `{{cli}} docs check` (frontmatter, живые ссылки, слишком большие файлы — разбить). Реестры (`INDEX.md`, `registry/*.md`, кроме `findings.md`) генерирует `{{cli}} docs index` — руками не править; `findings.md` пишется вручную.

## Типы агентов (`.claude/agents/`)
| Тип | Модель / усилие | Для чего |
|---|---|---|
| `dp-coordinator` | Opus / high | координатор модуля: план, контракты, копии, приёмка, шлюзы; скилл `start-to-do`; сам не ревьюит |
| `dp-engineer` | Sonnet / medium (сложная логика — `model: opus`) | код проекта и тесты к нему |
| `dp-researcher` | Sonnet / medium (сложная логика — `model: opus`) | прототипы, замеры, литература и данные, веб |
| `dp-writer` | Sonnet / medium | документы и тексты |
| `dp-mechanic` | Haiku / low | механическое: замены по шаблону, прогоны тестов/сборок готовыми инструментами, слияния без конфликтов |
| `dp-reviewer` | Opus / medium | ревью по риску (сложная логика, стыки контрактов, повторная доработка) после PASS в `{{cli}} accept`, пустой контекст; фокус — `uncertain` исполнителя; только чтение и перезапуск проверок; вердикт — `{{cli}} review` |
| `dp-status` | Haiku / low | сбор статуса агентов, веток и процессов — короткая сводка для главной сессии |
Модель можно переопределить при запуске (например, `dp-researcher` на более простой модели для поиска литературы). Исполнители и ревьюер агентов не порождают — только координатор.

## Настройка агентов
- Источник — файлы `.dpcli/agents/*.md` (обычный формат агента Claude Code: frontmatter `name, description, model, effort, tools/disallowedTools, skills` + текст). `.claude/agents/` генерирует `{{cli}} init` (подставляет плейсхолдеры) — править в `.dpcli/agents/`, потом снова `{{cli}} init`; изменённые руками файлы в `.claude/` без `--force` не перезаписываются.
- Ключи dpcli во frontmatter: `dpcli_role: coordinator|executor|reviewer|status` — роль в процессе; `dpcli_review: true|false` (для executor) — нужен ли ревьюер по риску после PASS (`checked`) или PASS сразу `accepted`.
- Свой тип исполнителя (например, `dp-designer`): положить `.dpcli/agents/dp-designer.md` с `dpcli_role: executor` и `dpcli_review`, выполнить `{{cli}} init`; после этого он допустим в `{{cli}} task new --type dp-designer`. Добавить строку в таблицу «Тип исполнителя» скилла `start-to-do` (`.dpcli/skills/start-to-do/SKILL.md`).

## Наблюдение
- Каждые 30 минут главная сессия запускает `dp-status` (или сама `{{cli}} status`) и пересказывает пользователю: что сделано (коммиты), кто работает над чем, зависшие, вопросы, ждущие решения.
- Зависание: у агента нет коммитов, событий (`{{cli}} status` помечает «⚠тихо») и изменений файлов > 30–40 мин, или процесс идёт дольше обычного. Разобраться (что делает, чей процесс), сообщить; долгие запуски — только так, без опроса по имени процесса (`pgrep -f` находит сам цикл ожидания, `pkill -f` — свою же оболочку):
  1. свой запуск — фоном средствами агента (`run_in_background`): о конце сообщают, ждать не надо;
  2. если нужен код выхода и ожидание в скрипте — `{{cli}} job start <имя> <таймаут_с> <команда…>` → `{{cli}} job wait <имя>` (ждёт PID, печатает код и хвост лога; таймаут обязателен — код 124);
  3. чужой процесс — ждать по PID (`tail --pid=PID -f /dev/null` с `timeout`), найдя его один раз; убивать — только по PID после `readlink /proc/PID/cwd` (своя копия).

## Шаблоны
**Задание координатору**: где работать (копия, ветка), план и связанные документы, что уже сделано (коммиты), решения пользователя, как вести (волны, копии на задачу, контракты до исполнителей, журнал, шлюзы, «стоп»), правила — ссылкой на этот документ (`{{workflow}}`), что вернуть в отчёте.

**Задание исполнителю** (скилл `start-to-do`): карточка `{{cli}} task new` + вывод `{{cli}} task show <ID>` (задача, копия и ветка, контракты с версиями, скоуп, не трогать, проверки приёмки, отчёт через `{{cli}} report`); особенности задачи — текстом рядом.

**Отчёт исполнителя/координатора**: что сделано (файлы, коммиты), числа приёмки, что не вышло и почему, открытые вопросы (`uncertain`), как проверить, пути к картинкам (если есть), обратная связь по `{{cli}}`. Исполнитель — `{{cli}} report <ID>` (те же поля в JSON) и коротко текстом координатору.

**Задание ревьюеру**: «Ревью задачи <ID>», копия и ветка задачи (модель — параметром запуска). Больше ничего: ни истории, ни пересказа отчёта, ни подсказок, что искать.

**Отчёт на шлюзе**: условие/развилка, варианты с ценой и последствиями, рекомендация, что ждёт решения, что продолжается независимо.
