# start-to-do — запуск задачи исполнителем

Аргумент: номер/название задачи из плана модуля (например `AM-7b`).

## 1. Задача и контракты
- Найти задачу в плане модуля: `{{cli}} plan <модуль>` (оглавление) → `{{cli}} plan <модуль> <раздел>`: скоуп, ключевые файлы, условия приёмки, оценка, зависимости.
- Стыки задачи: по `{{contracts_dir}}/<модуль>.md` (`{{cli}} plan <модуль> --contracts <раздел>`) — какие контракты задача использует или поставляет, их версии. Нет контракта для нового стыка — **сначала описать** (владелец, потребители, интерфейс, единицы, инварианты, версия) и добавить контрактный тест; расхождения с кодом — записать и раздать.
- Зависимости готовы? Если нет — может ли задача работать против контракта на подставных данных (данные из файлов, заглушки)? Иначе — не запускать.

## 2. Рабочая копия
```
git -C <копия модуля> worktree add <копия задачи> -b <модуль>/<задача> {{module_branch}}
```
(от актуальной ветки модуля, после вливания уже принятого; путь копии — по `task_copy` конфига, по умолчанию `~/{{project}}-<модуль>-<задача>`). Первичная подготовка новой копии (зависимости, генерация, импорт) — по правилам проекта.

## 3. Тип исполнителя
| Работа | Тип |
|---|---|
| код проекта и тесты к нему | `dp-engineer` |
| прототип, эталон, замеры, литература/данные | `dp-researcher` |
| документы и тексты | `dp-writer` |
| замены по шаблону, прогоны, работа готовыми инструментами | `dp-mechanic` |
Свои типы проекта — агенты `.dpcli/agents/*.md` с `dpcli_role: executor` ({{workflow}}, «Настройка агентов»). Модель можно переопределить (`model` в Agent), если задача явно проще или сложнее типа. Повтор неудачной задачи — новый исполнитель с более чёткой спецификацией (можно более сильную модель).

## 4. Карточка и задание
Карточка — `{{cli}} task new` (справка `{{cli}} task new -h`, `.dpcli/README.md`); проверки приёмки — из плана, исполняемыми командами:
```
{{cli}} task new <модуль> <ID> --type dp-engineer --title "…" --goal "1–2 фразы, зачем" --plan-ref "<заголовок раздела>" \
  --contract <имя>@<версия> --scope <путь> --dont-touch <путь> --test <фильтр тестов> \
  --check <имя> "<команда>" "<exit=0 | re:… | num:(…) <=X>"
```
(копия и ветка по умолчанию — из конфига (`task_copy`, `task_branch`, обычно `<модуль>/<ID>`); длинное — `--from card.json` или правкой JSON карточки.)
Задание исполнителю = вывод `{{cli}} task show <ID>` + особенности задачи текстом (замок GPU/CPU, большие данные — где лежат, куда класть картинки — в подпапку задачи каталога артефактов). Исполнителю: перед отчётом — пробный прогон проверок `{{cli}} accept <ID> --dry` (без события в журнале); полное задание одним куском — `{{cli}} task show <ID> --full`. Задачи нумеруются `<КОД>-<n>` (`{{cli}} task new <модуль>` без ID — следующий номер). Отчёт исполнитель сдаёт `{{cli}} report <ID>` и коротко текстом, в конце — `dp_feedback`.

## 5. Журнал
`{{cli}} event <ID> started --note "<тип>, <копия>"`; карточку и события коммитит координатор: `git add {{plan_dir}}/<модуль> && git commit -m "…" -- {{plan_dir}}/<модуль>`.

## 6. Приёмка (после отчёта)
Координатор **не читает код, диффы и логи задачи** — ревью делает `dp-reviewer`.
1. `{{cli}} report <ID> --show` → `{{cli}} accept <ID>` (в копии задачи; таблица PASS/FAIL).
2. FAIL → на доработку, ревьюер не нужен.
3. PASS у типа с `dpcli_review: false` (`dp-writer`/`dp-mechanic`) → событие `accepted`, дальше п. 5.
4. PASS у типа с `dpcli_review: true` (`dp-engineer`/`dp-researcher`) → событие `checked`; по умолчанию — принять по отчёту (`{{cli}} report <ID> --show`: проверки и `uncertain`) и `git diff --stat` → `{{cli}} event <ID> accepted --note "по отчёту"`. Ревьюер — только для сложной предметной логики/численных схем/стыка контракта/второй доработки/серьёзных `uncertain` ({{workflow}}, «Приёмка»): свежий `dp-reviewer` с заданием ровно: «Ревью задачи <ID>. Копия <путь>, ветка <ветка>.» — без истории и пересказа отчёта. Вердикт — в журнале: `{{cli}} review <ID> --show`. `accept` → `{{cli}} event <ID> accepted --note "по ревью"`; `rework` → замечания исполнителю (новому или тому же), после доработки снова п. 1 и свежий ревьюер. Спорное — вопрос ревьюеру/исполнителю.
5. Влить `<модуль>/<ID>` в `{{module_branch}}`, `{{cli}} accept <ID> --here --commit <слияние>` (затронутые проверки на ветке модуля), `git worktree remove` и удалить ветку, `{{cli}} event <ID> merged`; решения по ходу — `{{cli}} decide`.
